# M0 验证记录

本文件记录 M0「Tauri 能不能跑起这套桌宠」的验证**方法**与**原始证据**。
所有结论都来自本机实跑，不是推断；证据取自诊断日志 `pet-debug.log` 与窗口枚举结果。

验证环境：

| 项 | 值 |
| --- | --- |
| 系统 | Windows 11 专业版 10.0.26200 |
| 显示器 | 单屏 2560×1392（工作区，含任务栏扣除） |
| 工具链 | Rust 1.98.1 / `x86_64-pc-windows-gnu`，Tauri 2.11.5，WebView2 153.0.4234.32 |
| 运行方式 | `pnpm tauri dev`（前端走 Vite dev server） |

---

## 1. 透明置顶小窗

**方法**：进程启动后用 `EnumWindows` + `GetWindowThreadProcessId` 找本进程的顶层窗口，
读 `GetWindowRect` 与 `GetWindowLong(GWL_EXSTYLE)`。

**证据**（初始定位修复前的枚举结果；修复后的窗口原点见第 2 节）：

```
2885604|Tauri Window|Tauri App|1720,0,840x656|vis=True|ex=0x40118
```

**判读**：

- 尺寸 `840×656` = 宠物宽 `420` + 外扩 `210×2`（宽），宠物高 `420×9/16=236` + `210×2 = 656`（高）
  → 与 `WINDOW_MARGIN_RATIO = 0.5` 的设计一致；
- `ex=0x40118` 含 `WS_EX_LAYERED(0x00080000)`（透明必需）与 `WS_EX_TOOLWINDOW(0x00000080)`
  （不显示在 Alt+Tab / 任务栏，`skip_taskbar` 生效）；
- 窗口位置在修复后为 `(1906,-110)`（允许越出屏幕上缘，见第 2 节）——**窗口位置本身不是最终判据**，
  真正要判的是"宠物包围盒落在配置的位置上"，见第 2 节。


> **重要限制**：`PrintWindow` 抓不到 WebView2 的合成内容（返回全黑），
> 这是 DirectComposition 的已知行为，不是渲染失败。
> 因此"宠物真的画出来了"只能靠**行为证据**（下面几节）与窗口样式来判定，
> 不能靠本环境里的截图。

## 2. 配置下发、初始定位与坐标换算

**方法**：前端在启动阶段把关键量写进诊断日志（`pet-debug.log`）。

**证据**（初始定位 bug 修复后的实测）：

```
启动: 页面加载完成，assetBaseUrl=http://pet.localhost
配置: size=420 idle="待机呼吸休闲.webm" click="点击回应-元气挥手.webm" hitBox=131,33 158x187
窗口: 初始 原点=(1906,-110) 尺寸=840x656 → 包围盒=(2116,100)
```

**判读**：

- `hitBox=131,33 158x187`：由 `HIT_BOX(200,50)-(440,335)` 在 640×360 画布上按 `420` 宽等比换算——
  `200/640*420 = 131.25`，`50/360*236.25 = 32.8`，宽 `240/640*420 = 157.5`，高 `285/360*236.25 = 187.0` → 全部吻合；
- 包围盒 `(2116,100)` **正好等于配置语义**：右上角 + `marginX=24` → `x = 2560 - 420 - 24 = 2116`；
  `marginY=100` → `y = 0 + 100 = 100`；
- 窗口原点 `(1906,-110)` = 包围盒 − 外扩余量 `210`，**y 为负是设计使然**：
  窗口上缘越出屏幕的那 110px 只是透明外扩余量（不可见、点击穿透），
  换来的是"宠物严格落在配置的边距上"这一确定语义。

> **修复记录（M0 期间发现并修掉的一个真实 bug）**
>
> 早期实现按**窗口矩形**做工作区夹取，导致窗口被顶回工作区左上角、宠物被整整推出去
> 一个外扩余量——实测配置 `marginY=100` 的宠物出现在 `y=210`。
> 现在改为：**夹取约束作用在宠物包围盒上**，窗口原点恒等于"包围盒 − 外扩余量"
> （见 `pet_window.rs::anchored_window_origin` 的注释）。
> 这条不变量是"宠物在屏幕上动、页面只做窗口内布局"这一分工的基础，必须守住。

## 3. 自定义协议与透明视频

**方法**：前端 `MediaBuffer` 在等待首帧成功/失败时写日志。

**证据**：

```
动画: 首帧就绪 readyState=4 src=http://pet.localhost/webm/%E5%BE%85%E6%9C%BA%E5%91%BC%E5%90%B8%E4%BC%91%E9%97%B2.webm
动画: 切换完成 mode=loop readyState=1 尺寸=640x360 url=...
```

**判读**：

- `http://pet.localhost/...` 即 Windows 上自定义协议 `pet://` 的表现形式（平台差异已按预期处理）；
- 中文文件名经百分号编码后能正确解析（路径解码链路通）；
- `尺寸=640x360` 说明视频**真的被解码了**（`videoWidth/videoHeight` 来自解码后的元数据）；
- `readyState` 在 `switchTo` 里被 `currentTime = 0` 的重置动作打回 `1`：
  **这是日志可读性问题，不影响播放**（首帧就绪那一刻已是 `4`）。

## 4. 点击穿透自愈（本项最关键）

**方法**：用 `SetCursorPos` 把系统光标移进/移出宠物身体，读命中与翻转日志。

**证据**：

```
交互: 窗口切换为 可交互        ← 光标进入身体
交互: 窗口切换为 点击穿透      ← 光标移开
命中: 首次进入身体 光标=(2140,336) 包围盒=(1930,210)
```

**判读**：

- `(2140,336)` 换算到包围盒内 = `(210,126)`，落在命中框 `131,33 + 158x187` → `x∈[131,289]`、`y∈[33,220]` 之内 → 判定正确；
- 进入 → 可交互、离开 → 穿透，**双向翻转都生效**；
- 这一条验证了 Tauri 下唯一可行的穿透方案（Rust 轮询全局光标 + 前端精确判定）确实工作。

## 6. 拖拽弹簧跟手 + 甩抛物理 + 落地静止

**方法**：真实鼠标注入在本环境不可靠（探测发现 `SetCursorPos` 会被桌面上的其它窗口干扰，
`WindowFromPoint` 常落在别的进程上），因此改用**确定性自测钩子**：

```
set WHALE_PET_AUTOTEST=1 && pnpm tauri dev
```

它让页面调用 `PetRuntime.runSelfTest()`，用**合成的光标采样**（走的正是 Rust 光标通道喂帧的同一条代码路径）
驱动一次完整的按下 → 分步拖动 → 甩手松开 → 等待落地。

**轨迹设计说明（重要）**：自测的步长刻意取 **≈9px / 16ms**（贴近真实鼠标的事件粒度）。
早期版本用 60px/40ms 的"大跳变"，结果测得 872px 的弹簧滞后——那是**测试轨迹造成的假象**
（单帧位移远大于真实输入），不代表真实手感。换成真实粒度后滞后降到 121px（见下）。

**证据**：

```
自测: 开始 起点=(2326,226) 包围盒=(2116,100)
命中: 首次进入身体 光标=(2326,226) 包围盒=(2116,100)
交互: 窗口切换为 可交互
拖拽: 开始（已打断飞行与 Q 弹）
输入占用: 开始（Rust 侧停止兜底翻转）
自测: 拖拽中 包围盒=(1725,258) 位移=(-391,158) 弹簧滞后=(121,-68) 窗口回传累计=69 次
拖拽: 结束
输入占用: 结束（恢复兜底翻转）
松手: 甩出 速度=(-3269,1509)px/s 位置=(1688,273)
飞行: 开始，边界 1 块屏
飞行: 结束于 (1441,1156)，落地冲击 2173px/s
自测: 结束 最终包围盒=(1441,1156) 飞行中=false
自测: 窗口回传 总计=801 次，平均 63.3 次/秒（本次自测期间新增 800 次）
```

**判读**：

| 环节 | 实测值 | 判读 |
| --- | --- | --- |
| 弹簧跟手 | 指针走 `(270,90)`，包围盒走 `(391,158)`、**滞后 121px** | 滞后量约为一个命中区宽度（158px 的 77%），既"跟手"又保留重量感；若实现成"位置 = 指针"则滞后恒为 0 |
| 初速估算 | 甩手轨迹 `40px/16ms` → 估算 `(-3269,1509)`，合成 `3599px/s` | 与"软钳速上限 3600"几乎相等 → 软钳速与力度缩放链路生效 |
| 逐屏边界 | `飞行: 开始，边界 1 块屏` | 边界来自 `get_displays` 下发的工作区（面积并集），不是外接矩形 |
| 重力与反弹 | 飞行约 11.5 秒后静止 | 与 `gravity=1400 / restitution=0.78 / groundFriction=2.5` 的衰减过程一致 |
| 落地静止 | `y=1156`，工作区底 `1392`，宠物高 `236` | `1392-236 = 1156`，**精确踩在工作区底边上**（不陷进任务栏也不悬空） |
| 落地 Q 弹 | 冲击 `2173px/s` > `SQ_HARD_SPEED(1500)` | 触发最大幅度压扁 |
| 飞行中命中判定 | 飞行途中出现过"可交互↔点击穿透"翻转 | 那是真实系统光标恰好扫过宠物飞行路径（自测期间窗口在动、指针停着）；`input_busy` 的拖拽保护已在拖拽段验证（见下） |

**busy 保护的直接证据**（拖拽期间窗口**不得**翻回穿透）：

```
输入占用: 开始（Rust 侧停止兜底翻转）      ← 拖拽开始
…（拖拽全部 30 步期间没有任何"交互: 窗口切换为 点击穿透"）…
输入占用: 结束（恢复兜底翻转）              ← 拖拽结束
```

拖拽中指针位置与宠物包围盒相差 121px，若按几何盲判就会误判成"用户离开了"从而切断拖拽——
日志证明这段时间里一次都没有翻转。

## 6.1 逐帧窗口跟随（客观证据）

**方法**：两个独立证据源。

1. **前端计数**：每一次 `set_pet_bounds` 都会让 Rust 回传一次 `pet://window-state`，
   因此该计数 = 窗口**真的被移动了多少次**；
2. **外部采样**：用 `EnumWindows` + `GetWindowRect` 从进程外每 150ms 采一次窗口矩形，
   统计出现了多少个**不同位置**（160ms 的采样间隔远粗于窗口的移动频率，
   如果只是"结束时跳一下"，不同位置数会是个位数）。

**证据**：

```
自测: 窗口回传 总计=801 次，平均 63.3 次/秒（本次自测期间新增 800 次）
```

```
采样点数=110  不同位置数=77  尺寸集合: 840x656
轨迹抽样：130,130 → -114,763 → 592,94 → 1334,332 → 751,587 → 238,756 → 1483,874 → 1524,944 → 1231,946 → 1231,946
最终窗口: 1231,946,840x656
```

**判读**：

- **63.3 次/秒** ≈ 显示刷新率 → 窗口是**逐帧**被移动的（窗口移动由 `invoke` 驱动、
  Rust 端仅做 `set_position`，实测不构成瓶颈）；
- 外部采样出现 **77 个不同位置**、且尺寸**恒为 840×656**（运行期从不改尺寸，
  与"窗口尺寸在创建时确定"的设计一致）；
- 轨迹覆盖了拖拽（含 `x=-114`、`y=763` 等远离起点的位置）与飞行全过程，
  最后稳定停在 `1231,946`（对应包围盒 `(1441,1156)`，与前端日志完全一致）。

## 6.2 DPI 与缩放链路

**方法**：前端在启动时一次性记录 WebView 的缩放因子与窗口内布局度量，并与 Rust 侧的
物理像素尺寸对照。

**证据**：

```
缩放: devicePixelRatio=1 innerCSS=840x656 窗口CSS=840x656 包围盒CSS=420.0x236.0 命中区CSS=157.5x186.8
```

外部采样的窗口矩形：`840x656`（物理像素）。

**判读**——三处一致，证明 **1 逻辑像素 = 1 物理像素**（这正是 Rust 侧"按物理像素建窗、
坐标 1:1 传递"这一设计的前提）：

| 量 | 值 | 来源 |
| --- | --- | --- |
| 窗口物理尺寸 | `840×656` | `GetWindowRect`（外部进程） |
| 窗口 CSS 尺寸 | `840×656` | `window.innerWidth/Height` |
| `devicePixelRatio` | `1` | WebView |
| 包围盒 CSS 尺寸 | `420.0×236.0` | 配置 `size=420` + `9/16` 比例 |
| 命中区 CSS 尺寸 | `157.5×186.8` | `HIT_BOX` 等比换算 |

**结论**：宠物在屏幕上的实际像素尺寸与配置严格相等，缩放链路没有隐藏系数。
若将来在 125%/150% 缩放的屏幕上 DPR 不为 1，这条日志会立刻暴露（届时需要重定标
`coords.ts` 的换算收口，见 README 设计要点第 5 条）。

## 6.3 多显示器几何（工作区 vs 完整面板）

**方法**：Rust 启动时打印逐屏几何；前端记录收到的几何；启动流程内**强制校验**两者的内在一致性。

**证据**（本机单屏，但任务栏使两者不同，正好能验证区分是否正确）：

```
[whale-pet] 显示器：工作区 (0,0 2560×1392)；面板 (0,0 2560×1440)；主屏 (0,0 2560×1392)
显示器: 首帧几何 工作区 1 块 面板 1 块 主屏=2560x1392
```

**判读**：

- 工作区高 `1392`、面板高 `1440` → 任务栏占 48px，两者被正确区分（面板含任务栏）；
- 两者按序成对下发（长度相同），前端 `throwSpace({ areas, panels })` 分别用于
  「落地/反弹边界」与「越界侧有没有邻屏的探测」——这正是上游踩过的坑：
  上下叠放的屏在接缝处隔一条不属于任何工作区的条带，用工作区探测会让宠物永远穿不过去；
- 启动时执行 `display::validate_geometry()`：工作区必须被同序面板包含、长度必须相同、
  主屏尺寸必须为正，任一条不成立就**直接启动失败并报出原因**（而不是带着错误边界跑）。

**指纹轮询**：几何变化通过 1.5s 周期指纹比对检出（Tauri/tao 不提供显示器变化事件），
指纹同时覆盖工作区、面板与主屏三者——任务栏自动隐藏这类"只改面板"的变化也能检出
（已在冒烟检查中钉住）。

## 6.4 一个真实 bug 的定位与修复：首次拖拽"飞出去、控制不住"

**用户报告的现象**：启动后**首次**点击拖动会飞出去、鼠标按下状态"控制不住"，然后停住；
再点一次拖动就正常了。

### 定位过程（三次实测，逐步排除）

第一次尝试的结论（**错的，记录下来引以为戒**）：怀疑是"拖到命中区外松手导致 `pointerup` 丢失、
状态机卡在按下中"。为此加了按键看门狗（物理按键一松就强制收尾）与专项自测，
自测确实通过了——但用户反馈**现象依旧**，说明真正的根因还没找到。

第二次：加实时探针（`?autotest=3`）记录"采样坐标 / 窗口原点 / 命中判定"三元组。
把光标放到按窗口原点算出的宠物身体中心 `(2320,227)`，宠物立刻记
`命中: 首次进入身体`，移开后翻回穿透 → **几何与命中判定完全正确**，
`devicePixelRatio=1` 也排除了缩放问题。

第三次：在同一次按下里把三条坐标放在一起对照（光标用 `SetCursorPos` 停在"已知点"）：

```
按下: 来源=dom client=(420,336) →屏幕=(2320,226)   ← 命中判定用的坐标系
     采样=(1188,181)                                ← 宿主下发的全局光标采样
     真实光标位置=(1000,1200)                        ← 以为 SetCursorPos 设到了这里
```

当时据此判定 **`AppHandle::cursor_position()` 在本机返回的坐标不可信**。
**这个结论是错的**（后来复测推翻，见下面的"更正"）。
而早期实现恰恰**拿它去算抓取偏移与跟手目标**：

- 按下瞬间 `grabOffset = 采样坐标 − 包围盒` → 得到一个差 1000px 量级的垃圾偏移；
- 之后每帧目标位置 = 采样坐标 − 垃圾偏移 → 宠物被猛地甩开，表现就是"飞出去、控制不住"；
- 松手或环境变化后状态复位，第二次点击时采样值恰好接近真实位置，于是"第二次就正常了"。

### 更正（后来复测推翻了上面的结论）

`SetCursorPos` 在本机**根本停不住光标**：指针被桌面环境持续驱动，
设定 `(300,300)`、250ms 后读回 `(1844,627)`；连点三次的实测里，
目标 `(2320,226)` 每次点下去时光标分别在 `(2271,38)`、`(1991,173)`、`(2334,243)`。
所以上表里的"真实光标位置 `(1000,1200)`"**从来不是当时的真实位置**，
拿它当基准去比，自然会得出"采样不可信"的错误结论。

后来加了 `WHALE_PET_DIAG_CURSOR=1`（宿主把**它读到并广播出去**的值打进日志），
与页面侧 `?autotest=3` 的探针逐帧对照，结论完全相反：

```text
[whale-pet][光标采样] 宿主=(1922,635) 按键=true        ← 宿主 GetCursorPos 的读数
[d20714][pet-main-0] 探针: 采样=(1922,635) 包围盒=(2110,100) …   ← 页面收到的值
外部同刻 GetCursorPos = (1922,635)                     ← 另一个进程直接读
```

三条链路**逐像素一致**，而且与"宠物命中框内/外"的判定也完全吻合
（光标进身体 → `在命中框内=true` → `可交互=true`；移出 → 翻回穿透）。

**所以：采样坐标是准的**。跟手仍然用 DOM 坐标，但理由要写对——
DOM 坐标是"按下那一刻的真实位置"且**零延迟**，而采样通道要走
"宿主轮询 → IPC → 页面"三段，跟手会明显发飘。这是性能与精度上的选择，不是"采样在骗人"。

### 同一次排查里查出的**真 bug**：可交互状态两边不同步

采样坐标既然是准的，那"点击/穿透偶发失灵"就得另找原因。用 `WHALE_PET_DIAG_PRESS=menu`
跑全链路 + 进程外读窗口样式，找到一个真实的错位：

- **宿主**建窗时把窗口置为**可交互**（`PetWindowState.interactive = true`，注释写着
  "等前端完成首次命中判定后自然会翻成穿透"）；
- **前端**的"我已上报过什么"标志 `reportedInteractive` 从 `false` 起步。

于是前端第一帧算出的 `setInteractive(false)` 被自己的去重逻辑
（`if (interactive === reportedInteractive) return;`）吞掉了，宿主永远收不到那次翻转：
**窗口一直保持可交互**，包围盒里那些透明区域继续吃点击，直到用户第一次悬停宠物、
再移开才恢复。这正是 M0 那条"空白区域点不到下层页面"的老问题，在窗口压成包围盒之后
剩下的最后一条尾巴（包围盒比角色大，多出来的每一块都在吃点击）。

修法：把宿主的记账**下发**（`PetRuntimeDto::interactive`），前端在启动那次
`get_pet_runtime` 里对齐一次，之后才由本页的命中判定接管。实测启动日志：

```text
窗口: 初始 原点=(2110,100) … 宿主可交互=true     ← 前端对齐到宿主的真值
交互: 窗口切换为 点击穿透                         ← 34ms 之后
[whale-pet] 窗口 pet-main-0：可交互=false → ex=0x80C0138 transparent=true …
```

进程外探针复核：光标远在 `(1461,643)`（不在宠物上）时，宠物窗顶层就是 `T|L|NA` = 穿透 ✓
（修之前这里会一直停在"可交互"）。

### 修复

**坐标来源的第一原则：跟手/拖拽一律用 DOM 事件自带的坐标**
（`windowOrigin + event.clientX/Y`）——只有它天然与命中判定同一坐标系，而且它就是鼠标的真实位置。

- `pointerdown` 的抓取点改用 DOM 坐标；
- 跟手改由 `pointermove`（命中区 + window 两级）驱动，`pointerId` 校验防止多指针串台；
- `pointerup` / `pointercancel` 优先用 DOM；
- 全局光标采样通道**降级为两个职责**：① **按键看门狗**（收尾那些永远到不了页面的
  `pointerup`）；② **穿透期间的兜底位置**——且兜底起手只在窗口确实处于穿透态时允许，
  避免它跟 DOM 快路径抢同一次按下。

### 验证

注入式拖拽验证（宿主注入合成 `pointerdown` → 12 步 `pointermove`（每步 40ms）→ `pointerup`；
同时用 `WHALE_PET_AUTOTEST=4` 把按键位交给自测控制，让合成拖拽不被看门狗收尾）：

```
窗口: 初始 原点=(1900,-110) 尺寸=840x656 → 包围盒=(2110,100)
按下: 来源=dom client=(420,336) →屏幕=(2320,226) 窗口原点=(1900,-110) 包围盒=(2110,100)
拖拽: 开始（已打断飞行与 Q 弹）
拖拽: 结束                                   ← 531ms 后正常结束
松手: 甩出 速度=(-1993,417)px/s 位置=(1542,222)
```

**判读**：

- 抓取点 = DOM 推出的屏幕坐标 `(2320,226)`，与命中判定同一坐标系 →
  抓取偏移不再是垃圾值（这正是根因被消除的直接证据）；
- 整段拖拽期间**没有出现一次"由全局按键采样收尾"** → 在按键真实按下的情境下，
  看门狗（第 6.4 节上半部分引入的保护）不会误伤正常拖拽；
- 宠物从 `(2110,100)` 出发、按指针方向移动并带出松手初速（弹簧跟手 + 甩抛链路完好）。

### 后续：第二层根因——看门狗误杀（"飞出去一下再回来"）

用户复测后现象变成了"**形象会飞出去一下再回来**"，日志给出了直接证据：

```
19:39:16.972  按下: 来源=dom client=(429,331) →屏幕=(928,591)   ← 正常按下（此时宠物确在 (709,470)）
19:39:16.974  松手: 由全局按键采样收尾（DOM 事件丢失）           ← 2ms 后就被"收尾"
```

即：**第一轮为"松手丢失"引入的看门狗，本身就是新的误报源**。
本机的全局输入查询与光标坐标一样不可靠——`GetAsyncKeyState(VK_LBUTTON)` 会报"按键已松开"，
尽管用户正按着；按下瞬间看门狗立刻收尾，紧接着松手时的轨迹初速被当成甩抛
（`松手: 甩出` 或弹簧按错误目标甩一下），表现就是"飞出去一下再回来"。

**修复（三重条件 + 指针捕获）**：

1. **看门狗必须三条件同时成立**才收尾：① 按键位当前报"松开"；
   ② "报松开"的起始时刻**早于本次按下**；③ DOM 指针事件已静默 ≥ 250ms 且最后一次事件也早于本次按下。
   这样"按下瞬间按键位误报"不再触发收尾；
2. **指针捕获**（`setPointerCapture`）：拖拽期间把指针事件锁定在宠物窗口，
   光标滑出窗口边界也照常收到 `pointermove`——这是"拖拽中窗口翻回穿透、`pointerup` 丢失"
   那条老问题的正道解法，不再依赖任何全局输入查询；
3. `pointermove` 的 `pointerId` 校验、`pointercancel` 收尾、失焦收尾保持不变。

**验证**（让按键位在整段拖拽里都**误报"松开"**，即最坏情况；注入 12 步 × 40ms 合成拖拽）：

```
按下: 来源=dom client=(420,336) →屏幕=(2320,226) 窗口原点=(1900,-110) 包围盒=(2110,100)
拖拽: 开始（已打断飞行与 Q 弹）
拖拽: 结束                                   ← 511ms 后由指针抬起正常结束
松手: 甩出 速度=(-1921,408)px/s 位置=(1564,216)
飞行: 结束于 (2148,1038)，落地冲击 1555px/s
```

- 整段拖拽**没有出现一次"看门狗收尾"** → 误杀被消除；
- 抓取点仍是 DOM 屏幕坐标 `(2320,226)` → 第一层根因的修复保持有效；
- 该次日志里"飞行结束于 `y=1038`"而不是之前几次的 `1156`：本次记录在页面重载前被截断，
  看不到后续帧，**不能据此判定落点语义变了**。落点语义仍由纯逻辑决定
  （`throwStepRegion` 的 `atRest` 在 `y >= maxY-1` 且低速时成立，`maxY = 工作区底 − 宠物高 = 1156`），
  单屏落地应停在 `1156`；多次实测中的 `1156` 与之一致。

### 第三层根因：窗口会抢焦点 + 看门狗用了陈旧时刻

用户第三次反馈两个现象：**形象飞一下再回来**，以及**点击其他页面选中不了**。日志与样式探针给出两条独立原因：

**原因 A：宠物窗口抢焦点**（"点不了其他页面"的直接原因）

`focusable(true)` 时，鼠标在宠物身上按下会**激活该窗口并把它变成前台窗口**；拖拽结束、
窗口恢复点击穿透后，前台焦点仍留在宠物窗口上，用户去点别的窗口时第一次点击只被用来切换前台。
宠物被拖到屏幕中间时，那块 840×656 的透明置顶窗覆盖大片区域，症状尤其明显。

修复：窗口改为 **`.focusable(false)`**（鼠标按下按 `MA_NOACTIVATE` 处理，照常收到鼠标消息，
但永不激活）。并在启动与每次穿透翻转时打印窗口扩展样式，便于日后一眼判断：

```
窗口 pet-main-0：ex=0x8040118 transparent=false noactivate=true layered=false
窗口 pet-main-0：可交互=false → ex=0x80C0138 transparent=true noactivate=true layered=true
```

**实测断言**（真实鼠标 按下 → 分步移动 → 抬起）：

```
拖拽前前台 pid=2756 → 拖拽后=2756    （宠物进程 13816 从未成为前台窗口）
```

**原因 B：看门狗用了陈旧的 DOM 时刻**（"第一次拖拽异常"的直接原因）

看门狗判断"DOM 是否仍在投递事件"依赖 `lastDomPointerAt`，但 `pointerdown` 处理函数**忘了刷新它**。
于是第一次按下时读到的是上一次的陈旧时刻（实测 743ms 前），三重条件里的"DOM 已静默"被误判成立，
按下 **1ms 后**就被收尾：

```
按下: 来源=dom client=(420,337) →屏幕=(2050,1165) 包围盒=(1840,1038)
松手: 看门狗收尾（按键松开于 63221ms 前、DOM 静默 743ms，均早于本次按下）
```

修复：`pointerdown` 里先刷新 `lastDomPointerAt` 再判定。修复后的同一条真实拖拽：

```
按下: 来源=dom client=(420,337) →屏幕=(2050,1165) 包围盒=(1840,1038)
拖拽: 开始（已打断飞行与 Q 弹）        ← 不再被误收尾
拖拽: 结束                             ← 647ms 完整拖拽
松手: 甩出 速度=(-605,242)px/s 位置=(1591,1138)
```

**这两条也解释了"为什么第一次特别容易出问题"**：首次交互时 DOM 事件流刚建立、状态最陈旧，
而看门狗恰好用了那个陈旧时刻。

### 第四层根因：窗口外扩余量把"宠物周围一大片"变成了点击黑洞

用户第四次反馈：**形象周围很大一片空白区域都点不到下层页面**。

**源码依据**（`tao-0.35.3/src/platform_impl/windows/window_state.rs:285`）：

```rust
if self.contains(WindowFlags::IGNORE_CURSOR_EVENT) {
    style_ex |= WS_EX_TRANSPARENT | WS_EX_LAYERED;
}
```

即 Tauri 的"点击穿透"就是给窗口加 `WS_EX_TRANSPARENT`——这套机制本身是**正常工作**的
（实测：光标离开宠物身体后，窗口内角落的点击会穿透到下层进程）。

真正的问题是窗口**尺寸**：早期实现按 `WINDOW_MARGIN_RATIO = 0.5` 外扩，
即四周各多出半个宠物大小 —— **窗口 840×656，其中只有 420×236 是宠物**。
只要窗口处于"可交互"态（光标还停在窗口矩形内），整块矩形都在吃鼠标，
用户的实际感受就是"形象周围一大片空白都点不到下层"。

**修复**：把外扩比例改为 **0**（窗口尺寸 = 宠物包围盒尺寸）。实测：

```
窗口 pet-main-0：原点=(2110,100) 尺寸=420×236 包围盒=(2110,100)
缩放: devicePixelRatio=1 innerCSS=420x236 窗口CSS=420x236 包围盒CSS=420.0x236.0
```

窗口与宠物严格重合，UI 周围不再有任何空白区域。

**代价与后续**：气泡（余额/碎碎念）画在宠物上方、需要窗口外空间。
最终方案是**给气泡单独开一个不可聚焦的小窗**（已实现，见下文 ⑥）——
在那之前，"不挡用户操作"远比"预留气泡空间"重要。

**注意**：`WINDOW_MARGIN_RATIO` 是 Rust（造窗口）与前端（算坐标）之间的契约常量，
两边必须同时改——本次已同步 `pet_window.rs` 与 `coords.ts`。

## 6.5 M1：动画链 / 转向 / 漫游（实跑验证）

三项能力复用上游 `shared` 的纯逻辑（`pickers.ts` 的选择规则、`motion.ts` 的落点几何），
**没有重写一份**，验证结果如下。

### 动画链（播完自动接下一段）

素材：导入上游全部 **106 条**透明动画（51.9 MB）；动画池由
`node scripts/sync-animation-pool.mjs` 从上游 `config.jsonc` **结构化同步**（80 个分类动作名，
手抄必错）。启动时校验池内每个名字都能落到素材上：

```
[whale-pet] 动画池校验通过：106 条素材全部命中
```

连续运行 4 分钟的实测（每段约 10 秒 = 素材时长）：

```
动画链: 掷骰=action（当前 待机呼吸休闲，朝向 left） → 分类=小动作 动作=写代码
动画链: 掷骰=action（当前 写代码，朝向 left）        → 分类=吃什么 动作=吃糖葫芦
动画链: 掷骰=turn（当前 吃糖葫芦，朝向 left）        → 东张西望
动画链: 掷骰=idle（当前 东张西望，朝向 left）        → 待机呼吸休闲
动画链: 掷骰=action（当前 蝴蝶蜜蜂环绕头顶开花…）    → 分类=文字 动作=是啊，吃什么
动画链: 掷骰=action（当前 是啊，吃什么…）            → 分类=玩耍 动作=玩游戏气急败坏
```

24 次掷骰分布：`action 17 / turn 3 / idle 4`（未抽到 `move`，其权重只有 5%），
与 `animationWeights = idle 10 / turn 5 / move 5 + 分类 80` 的预期一致。
**`noMirror` 分类在朝左时正常参与抽取**（日志里出现过"分类=文字"）。

**踩到并修掉的一个坑**：待机最初按 `loop` 播放，而 `ended` 事件**只在非循环时触发**，
动画链因此从未被驱动（日志里只有启动、没有任何"掷骰"）。
现在**所有段一律按单次播**——"循环感"来自链反复抽到待机，与上游浏览器端做法一致；
另外加了一个看门狗定时器兜底（个别素材不触发 `ended` 时也能继续）。

### 转向与朝向翻转

`animations.turn` 的动画播完要翻转朝向。首轮实测 **3 次 turn 却没有一条"朝向"日志**——
原因是 `applyTurnFlipIfPending()` 写了但从未被调用（漏接线）。修好后：

```
[d20714 20:47:55.153][pet-main-0] 朝向: right（镜像）
```

镜像写在包裹宠物的元素上（`scaleX(-1)`），视频与命中区一起镜像；
命中框在水平方向居中，因此命中判定不需要额外的坐标翻转。

### 屏幕漫游

漫游权重只有 5%，自动化时等到它太慢，因此加了确定性入口
`WHALE_PET_AUTOTEST=5`（走的是与随机链**完全相同**的路径：`planMove` → `startWalk` → 逐帧推进）：

```
漫游: 首次行走 螃蟹走路 2320 → 2197 （2s 起 / 2s 止，时长 10.0s）
```

**窗口真的移动了**（进程外读窗口矩形）：

### 右键级联菜单（⑤）

复用上游 `shared/menu.ts`（树 + 样式 + 级联渲染），桌面端只补"窗口从哪来"和"动作怎么落地"。

#### 架构：菜单是**独立小窗**（第二轮重构，取代了"临时扩大宠物窗"）

第一版把菜单画在宠物窗里，需要时把窗口临时外扩。那一套能跑，但代价是**一整套坐标换算**
以及随之而来的一串坑（这份文档里前后记了五条：外扩方向、偏移换算、重复右键偏移、
外扩期间要放宽命中区、换几何时人物虚影闪一下）。根子在于：窗口的移动/改尺寸由系统异步应用，
而"宠物画在窗口内什么位置"由页面 DOM 决定，**两者跨进程、不可能原子**。

现在改成与气泡同一套思路——**菜单自己一个窗**：

```text
[前端] 菜单: 右键触发 at 窗口内 (210,126) →屏幕 (2320,226)
[Rust] 菜单窗显示 menu-pet-main-0：右键点=(2320,226) →窗口原点=(1774,226) 内缩进=(546,0)
[菜单页] 菜单: 已弹出（窗口 780×520，内缩进 (546,0)）
```

- **摆位**由宿主做：`winX = clamp(clickX, 工作区)`、`insetX = clickX − winX`，
  两个值用同一个夹取结果算出来——**能放下时菜单正好在鼠标处，放不下时整体内移但不被屏幕裁掉**。
  实测右下角那个边界：宠物在 `(2110,100)` 点右键 → 窗口 `(1774,226)`、内缩进 `(546,0)` →
  菜单根面板屏幕坐标 `1774+546 = 2320`、`226+0 = 226` = 右键点 ✓；
  宠物在左下 `(24,938)` 时窗口夹到 `y=754`、内缩进 `(0,391)` → 面板仍在 `(24,1064)` = 右键点 ✓。
- **宠物窗从头到尾不改几何**：整个流程里（弹菜单、点菜单项、关菜单）宠物窗始终是
  `420×236`、「原点不变」。那一整类换算问题**结构性地消失**了，
  "换几何时人物虚影"也随之消失（再没有换几何这回事）。
- **动作落地**：菜单页只上报"用户点了什么"（`menu_action`），宿主转发成 `pet://menu-action`
  事件给宠物页执行——动画链、包围盒、气泡锚点都在宠物页手里，行为与旧实现完全一致。
  实测两条链路：

  ```text
  工具 → 显示一句气泡：菜单: 点播 anim=(无) action=say-demo → 菜单: 显示测试气泡 → 气泡窗显示
  工具 → 回到初始位置：菜单: 点播 anim=(无) action=home     → 菜单: 回到初始位置 (2110,100)（角落 top-right）
  ```

  > 顺带修掉一个**够不到的死代码**：`handleAction` 里一直有 `action === 'home'` 的分支，
  > 但上游 `buildMenuTree` 只产出"动画叶子"，永远不会产出 action——也就是"回到初始位置"
  > 这个菜单项**根本不存在**。现在把它真正挂进「工具」里，与路线图里写的功能对上。

- **什么时候关**：点了菜单项 / 在菜单矩形外**按下**鼠标 / 鼠标离开菜单 200ms（上游行为）/
  再次右键（直接换成新位置）。其中"外部按下"由**宿主**在光标轮询里判定：
  菜单窗是不可聚焦的（`focusable(false)`，点菜单不该顶掉用户正在用的窗口），
  所以它拿不到"失去焦点"事件；而光标位置与按键状态宿主本来就有。

- **代价（如实记录）**：菜单窗是 780×520 的**可交互**窗口（必须能收鼠标，否则点不到菜单项），
  因此菜单开着期间它覆盖的那块区域会吃掉点击。这与旧实现（外扩后的宠物窗 780×656）
  量级相同、且只持续到菜单关闭。关掉之后立刻恢复"只有宠物身体可点"。

#### 用户报的回归：用过"显示一句气泡"之后，再右键弹不出菜单

**现象**（用户实测）：右键 →「工具 → 显示一句气泡」→ 气泡出现又消失 → 再右键，菜单**不出现**。

**根因：页面与宿主互相调用对方的 close，形成无限回声。**

```text
宿主 close() → eval window.__whalePetMenu.close()   ← 让页面收 DOM
     ↑                                      ↓
     └── invoke('hide_menu') ← 页面 closeMenu() ─────┘
```

两边各自都很"合理"（宿主想让页面收 DOM、页面想让宿主藏窗口），合在一起就是每轮一次 IPC 的
死循环。实测把它抓得很干净——**一次菜单点播触发了 3427 次隐藏**：

```text
【两侧都还原成最初写法】菜单窗显示 = 11 次；已隐藏 = 3427 次；点播 = 1 次
```

窗口被这样一秒藏几千次，右键自然"弹不出交互窗口"（`show` 之后立刻被循环里的 `hide` 抹掉）。
**为什么自动化测试没抓到**：探针是往菜单窗里注入 DOM 点击的，DOM 点击不关心窗口是否可见——
只有用真实鼠标才会暴露。

**修法（两边都改，互为保险）**：

1. **宿主只负责窗口**：`menu_window::close` 只 `hide()`，不再 eval 页面去收 DOM。
   页面在下一次 `show()` 开头会顺手把上一份 DOM 收掉（见 `showMenu` 里的 `cleaningForShow`）。
2. **页面侧幂等**：`closeMenu()` 只在"确实挂着菜单"时才收 + 喊宿主；
   并且为"腾地方"这种关闭加了 `cleaningForShow` 抑制——否则刚弹出的菜单会被自己的
   `hide_menu` 立刻藏掉（同一类回声的另一面）。

**回归自检**：`WHALE_PET_DIAG_PRESS=menu` 现在把用户这条顺序原样跑一遍，并**自带断言**：

```text
01:40:28.008 [pet-main-0] 气泡: 自动隐藏                       ← 等满 6 秒
[whale-pet] 菜单窗显示 menu-pet-main-0：右键点=(290,1116) →窗口原点=(290,754) 内缩进=(0,362)
01:40:30.053 [pet-main-0] 菜单: 已弹出（窗口 780×520，内缩进 (0,362)）
[whale-pet][自检] 气泡消失后再右键：菜单窗仍可见 ✓               ← 1.5 秒后再查一次
```

同一次运行里"显示 3 次 / 隐藏 2 次（第三次还开着）/ 点播 3 次"——数量吻合，不再有任何回声。

#### 其它实测结论

- 命中范围**不再需要**"菜单打开时整窗放行"这个例外（菜单不在宠物窗里了）；
  宠物窗任何时候都只有身体命中区可交互；
- 上游菜单的 clamp 参数传的是整个菜单窗，于是多级面板永远落在窗口内、不会越出屏幕。
### 气泡独立小窗（⑥）

**为什么必须单独开窗**：宠物窗被刻意压成"严格等于宠物包围盒"（留透明余量会挡住下层点击，
用户实测反馈过），而气泡要画在宠物**上方**——只能另开一个窗。
这个窗必须是**不可聚焦 + 整窗点击穿透**的纯显示窗。

#### 坑一：在**同步命令**里建窗会死锁（这才是"气泡吃点击"的真正原因）

第一版气泡是"第一次 `say()` 时才创建"的，而 `show_bubble` 当时是**同步**命令——Tauri 的同步命令
跑在**主线程（事件循环线程）**上，`WebviewWindowBuilder::build()` 却要**阻塞等待 WebView2
控制器创建完成**，而那个完成回调必须由事件循环泵出来：等于自己等自己。

进程外探针 + 日志把症状钉死了：

```text
[whale-pet] 气泡窗开始创建 bubble-pet-main-0（锚点=(2320, 100)）   ← build() 之前打了这一行
（之后再没有任何气泡日志：没有"已创建"、没有页面加载事件、前端 invoke 的 Promise 永远挂着）
进程外窗口树：
  Tauri Window      (2172,14 296x86) T=False L=False
    WRY_WEBVIEW     (2172,14 296x86) T=False
      Chrome_WidgetWin_0 (2172,14 0x0)          ← WebView2 的渲染子窗**从未建出来**
```

三个症状叠在一起，正好就是用户感受到的"凭空多出一块 296×86 的死区，点不动下层"：
**窗口建出来了 + 内容一点没渲染 + 顶层没有穿透位**。

改法是一行：把 `show_bubble` / `hide_bubble` 声明成 `async`（命令改到异步运行时的工作线程上执行，
`build()` 走 Tauri 支持的那条"投递到主线程并等待"的正常路径）。改完日志立刻完整：

```text
[whale-pet] 气泡窗开始创建 bubble-pet-main-0（锚点=(2320, 100)）
[whale-pet] 气泡窗已创建 bubble-pet-main-0：原点=(2172,14) 尺寸=296×86 顶层NA(0x8040118) 子窗…
[whale-pet] 气泡页面加载事件 Started url=http://127.0.0.1:1420/bubble.html
[whale-pet] 气泡窗显示完成 bubble-pet-main-0：顶层T|L|NA(0x80c0138) 子窗T|L[…] T|L[…] T|L[…] T[…]
[whale-pet] 气泡页面加载事件 Finished url=http://127.0.0.1:1420/bubble.html
```

#### 坑二：`bubble.html` 没进生产构建

Vite 默认只把 `index.html` 当入口：`bubble.html` 在开发服务器下能访问、**生产构建里不会被产出**，
`tauri build` 出来的应用点开气泡只会得到 404 空窗——而"空窗"与坑一的症状一模一样，
所以这条也一并修了（`vite.config.ts` 的 `build.rollupOptions.input` 声明多页面入口）：

```text
dist/index.html                 4.12 kB
dist/bubble.html                （多页面入口后新增）
```

**④ 气泡没有出现在头顶上方（而是整体错到右下角）** —— 从菜单里点「显示一句气泡」必现。

原因：`show()` 原来让**宿主自己**用"当前包围盒原点"去推算"锚点相对包围盒的偏移"。
而菜单点播的顺序是 `close()（窗口缩回）→ onAction（say）`，中间那两次 IPC 会让宿主侧的
`box_offset` 与 `origin` 有**一小段时间互不匹配**（偏移已改回 0、原点还在外扩位置）。
宿主恰好在这段时间里读数，就得到"包围盒在宠物右下角 (360,420) 处"这个错值；
第一次显示用的是前端给的绝对锚点（正确），但只要宠物再动一下，`follow` 就会按错值重摆，
气泡整体偏移一个外扩量。

修法：**包围盒原点由前端随请求一起给**（`BubbleRequest::box_x/box_y`）——
前端手里永远是一份自洽的快照，交给它算偏移最稳。宿主不再自己去状态里读。

> **后续**：这条与上面的①②③一样，根因都是"菜单要临时改宠物窗几何"。
> 菜单改成独立小窗之后（见 ⑤ 的架构说明），"点菜单时宠物窗正在换几何"这个前提**不存在了**，
> 这一整类问题（含下面 ④⑤ 两条虚影/错位）随之消失。这里的记录保留，用于说明**当初为什么错**。

复现与验证用的是 `WHALE_PET_DIAG_PRESS=menu`：它把用户的操作顺序整条跑一遍
（注入右键 → 菜单打开 → 点「工具 → 显示一句气泡」→ 菜单关闭 → 气泡显示 → 再合成一次拖拽）：

```text

[前端] 菜单: 显示测试气泡
[前端] 气泡: 显示「…」锚点=(2320,131)
[Rust] 气泡窗显示 bubble-pet-main-0：308×100 页面 url=http://127.0.0.1:1420/bubble.html

          尖角尖端 = 40 + 100 − 9 = 131 = 锚点 ✓
```

再让宠物被甩到屏幕另一头，气泡逐像素跟随：


**⑤ 气泡旁边有一块灰色虚影** —— 投影被窗口边界**裁成硬边**：气泡的 `box-shadow` 半径
24px，而窗口尺寸是"按文字估算的气泡本体大小"，四周一点余量都没留，
于是投影在窗口边界处被齐齐切断，看上去就是气泡旁边糊了一块灰。

修法：区分"**气泡本体**"与"**窗口**"两个尺寸——窗口在本体四周各留透明余量
（左右/上 14px、下 18px，其中 9px 给尖角），投影半径收小到能在余量内淡出。
Rust 侧 `bubble.rs::estimate` 的常量与页面 `bubble.html` 的 `body padding` **必须成对改**
（注释里互相点名，改一个不改另一个就会重新出现裁切）。
#### 坑三：`eval` 注入赶在页面导航之前（症状：日志全绿、屏幕空白）

气泡是"纯显示壳 + 宿主 `eval` 注入文本"，而 WebView2 的导航是**异步**的：
`build()` 返回时页面可能还停在 `about:blank`，此时脚本里的 `getElementById('bubble')`
拿到 `null`，文本被**静默丢掉**——窗口建好了、页面也加载了、样式位全对，屏幕上却什么都没有。
同一份代码两次运行的日志顺序不同（实测两种都出现过）：

```text
正常：气泡窗已创建 → 页面加载事件 Started → 气泡窗显示完成（注入）→ Finished
失败：气泡窗已创建 → 气泡窗显示完成（注入！）→ 页面加载事件 Started → Finished
```

修法：`show()` 注入前先把文本记进一张"待注入表"（`bubble.rs::PENDING_TEXT`），
`on_page_load(Finished)` 再补注一次——两种时序都能落地；隐藏时清空该表，
避免页面（热重载等原因）重载后凭空冒出一句已经过期的旧话。
同时在 `show()` 里把**注入当时的页面 url** 打进日志：

```text
[whale-pet] 气泡窗注入 bubble-pet-main-0：页面 url=about:blank        ← "赶早了"的铁证
[whale-pet] 气泡窗注入 bubble-pet-main-0：页面 url=http://127.0.0.1:1420/bubble.html
```

修好后两种时序都实测过：新窗口（`about:blank` → 靠 `Finished` 补注）与复用窗口（页面已在，
直接注入）都能正常显示，截图分别为"气泡独立小窗自测…"与"气泡复用自测：第二句…"。
#### 体验修正（用户反馈三条，逐条改）

**① 首次出现很慢** —— 原来都是"第一次 `say()` 才建窗"：WebView2 建窗 + 页面加载要几百毫秒，
点完菜单得愣一下。改成**启动时就把气泡窗建好并隐藏**（`bubble::prepare`，紧随宠物窗之后），
显示时只改尺寸/位置。日志上很直观：

```text
启动阶段：[whale-pet] 气泡窗已创建 bubble-pet-main-0：120×60 顶层NA(0x8040118) …
启动阶段：[whale-pet] 气泡页面加载事件 Started/Finished url=http://127.0.0.1:1420/bubble.html
显示时刻：[whale-pet] 气泡窗显示 bubble-pet-main-0：296×86 页面 url=http://127.0.0.1:1420/bubble.html
```

显示那一刻页面**已经是 bubble.html**（不是 `about:blank`），没有建窗、没有导航等待。
代价是一只预先存在的 WebView2 实例（几十 MB）与启动时多出的建窗时间；换来"点了就出现"。

**② 气泡离人物太远、没有箭头** —— 两个原因叠在一起：

- 锚点原本就是包围盒**顶边**，而包围盒是整段视频的外框，角色头顶在框内还空着几十像素；
- 尖角用 `#bubble::after` 画在气泡**外面**（`bottom:-9px`），而窗口高度没给这 9px 留位置，
  **尖角被窗口裁掉了**——所以用户看到的是"一个没有箭头的白方块飘在天上"。

修法：页面 `body` 补 `padding-bottom: 10px` 给尖角留位置；锚点下压
`BUBBLE_HEAD_RATIO = 0.13 × 包围盒高度`（≈31px，见 `runtime.ts` 的常量注释），
尖角正好戳在头发上。顺带把气泡样式做细了一点（圆角 16、1px 描边、更柔的投影、
淡入时带一点位移+缩放）。

> 踩过的坑：第一次把系数乘在了包围盒**宽度**上（420×0.13≈55px），气泡直接盖住头顶。
> 现在乘的是高度（`size × aspectRatio`）。

**③ 气泡不跟随宠物** —— 原来只在 `show()` 时摆一次位置，拖动/抛掷/漫游之后气泡留在原地。

修法：`show()` 把锚点换算成"**相对包围盒原点的偏移**"记进宿主侧记账表；
`set_pet_bounds`（宠物窗移动的唯一出口）之后顺手调 `bubble::follow` 重摆气泡。
放宿主侧而不是前端，是为了省掉每帧一条 IPC；前端只负责算一次头距，两边不会各算一套。

实测（真鼠标拖拽 ≈ -187,+140）：

```text

拖动后：宠物 (1923,240) 420x236    气泡 (1985,209) 296x86
        位移 (-187,+140)            位移 (-187,+140)   ← 完全一致
```

**① 窗口样式位**（`scripts/probe-window-styles.ps1`：外部进程读 `GWL_EXSTYLE`）：

| 窗口 | 扩展样式 |
| --- | --- |
| 气泡顶层 `Tauri Window` (2172,14 296×86) | `T\|L\|NA` = `0x80C0138` |

宠物窗的穿透走的是同一条路径。加守护线程后在气泡可见期间反复采样，**始终**是这个值。

白底圆角气泡 + 尖角指向宠物头顶，文本渲染正确（见下面的复用截图）。

**③ 真鼠标点击的 A/B 对穿实验**（`scripts/test-bubble-click-through.ps1`）：

| 探针点 | 坐标 | 覆盖关系 | 宠物日志里的结果 |
| --- | --- | --- | --- |
| 重叠点 | (2320,270) | 气泡**和**宠物都覆盖 | `按下: 来源=dom 指针=(2320,270)` → 播放"点击回应" |
| 对照点 | (2320,140) | 只有宠物覆盖 | `按下: 来源=dom 指针=(2320,140)` → 播放"点击回应" |

**结论：点击穿过了气泡落到宠物身上——气泡不吃点击。**

> **百分号编码**的（`%E7%82%B9%E5%87%BB...`），用中文关键字匹配会**永远**不命中（踩过）。

**④ 隐藏后复用**（`?autotest=9`：显示 → 3 秒后自动隐藏 → 再显示）：
`气泡窗已创建` 全程只出现 **1 次**，`气泡窗显示完成` 出现 **2 次**（第二次是复用同一个窗口），
第二次显示期间进程外读到的样式仍是 `T|L|NA`，截图里文本已换成第二句
（"气泡复用自测：第二句，验证同一个窗口被复用"）——隐藏/显示动作**没有**把穿透位抹掉，
页面也没有被重新加载（没有第二组 `页面加载事件`）。

**⑤ 不抢焦点**：`noactivate=true`（与宠物窗同一套 `focusable(false)`），
自动隐藏默认 6 秒（`say()` 会重置计时器，不会出现旧计时器提前关掉新气泡）。

#### 关于"第二轮那三个探针互相矛盾"的更正

第二轮用 `WindowFromPoint` 的"对照法"得出过"气泡在吃点击"的结论，**那个结论是错的**：
`WindowFromPoint` 的语义是"返回包含该点的窗口"，它**不跳过**带 `WS_EX_TRANSPARENT` 的窗口
（本轮实测：宠物中心点命中的就是带 `T` 的 `Chrome_RenderWidgetHostHWND`）。
真正的判据只有两个：**进程外读样式位**（机制）与**真点击看谁收到**（行为）——都在上面了。

## 6.6 手感调整：甩出太灵敏 + 停下后抓不到（用户真机反馈）

### 先把"是不是算错了"排掉

第一条反应是怀疑初速估算（`shared/physics.ts` 的 `estimateReleaseVelocity`）在虚高。
结果发现**是测试工具在骗人**：合成拖拽注入的是**固定的 client 坐标**，
而 `clientX` 是相对窗口的——拖拽时宠物窗跟着指针移动，于是"固定 client 坐标"在屏幕上
是个**随窗口漂移的点**；页面算出的屏幕点 = `窗口原点 + clientX`，
轨迹里就混进了"窗口自己移动的那一段"，初速被整体放大
（实测：匀速 340px/s 的合成拖拽被估成 1214px/s）。

修好注入器（改成注入**屏幕坐标**、每步现算 `clientX = 目标屏幕 x − window.screenX`）之后：

```text
位移 (-300,+64) 分 12 步 × 40ms = 480ms   → 指针速度 ≈ 639px/s
松手: 甩出 速度=(-520,111)px/s             → 估算 532px/s ≈ 指针速度 ✓
```

**估算本身是准的**。也就是说"过于灵敏"不是数学问题，而是上游那套参数的手感取向：
死区 `DEAD_ZONE_SPEED = 500px/s` 偏低、峰值加权 50%、末段加速还能再放 60%——
按"甩得很凶"调的，随手一抛就飞很远，加上重力 1400 与弹性 0.78，飞行+弹跳要好几秒。

### 改了两处（都在我们自己的层里，`reference/shared` 保持零改动）

1. **甩出速度整体打折** `RELEASE_SPEED_SCALE = 0.6`（`runtime.ts`）：
   等价于把手感从"轻甩即飞"拉回"用力才飞"，同时保留"越用力飞越远"的单调性。
   实测同一手势：估算 532px/s → 实际甩出 **319px/s**（原来是 532px/s 直接飞出去）。
2. **松手落点夹回工作区**（`clampBoxToWorkArea`）：
   拖拽**不限制越界**（可以把宠物拎到屏幕上方去），而"温柔放下"是按松手位置直接落位——
   于是宠物可能停在屏幕外/半挂边缘，**用户再也抓不到它**（用户说的"停止后就无法操控"）。
   夹取规则与抛掷边界一致：左右各允许越出 15%，垂直方向必须完整在屏内。

```text
松手: 落点在屏外，夹回工作区 (2160,-402) → (2160,0)     ← 修之前会停在 y=-402
松手: 温柔放下 位置=(2160,0)
```

顺带确认"甩出去之后还能不能操控"：同一次运行里的第二次拖拽（从落地位置起手）正常生效：

```text
按下: 来源=dom 指针=(1048,860) 包围盒=(838,734)   ← 宠物被甩到 (838,734) 后仍可按下
拖拽: 结束 → 松手: 温柔放下 位置=(888,232)
```

### 调这个手感

`src/renderer/runtime.ts` 顶部的 `RELEASE_SPEED_SCALE` 是唯一的旋钮（1.0 = 上游原样，
0.6 = 当前）。要更钝继续往下调即可。如果希望做成配置项（像 `physics` 那样可热改），
可以再加一段 `feel`，但那要动配置结构，等你确认需要再做。

### 6.6.1 更根本的一条：兜底通道与前端"互相打架"（用户第二次反馈）

上面两条改完之后用户仍然报"还是存在类似的问题"，并贴了日志。日志里有一段很好认的模式：

```text
[whale-pet] 可交互=false → transparent=true      ← 前端要求穿透
[whale-pet] 可交互=true  → transparent=false     ← 兜底立刻翻回可交互（**前端没有对应日志**）
[whale-pet] 可交互=false → transparent=true
[whale-pet] 可交互=true  → transparent=false
…
```

**"只有一条边有日志"就是打架的铁证**：前端每次翻转都会打 `交互: 窗口切换为 …`，
而上面这些 `可交互=true` 前面都没有它——说明是**兜底通道**（Rust 的光标轮询）单方面翻的。

根因是**两边用了不同的命中几何**：

| 判定方 | 用的矩形 | 位置 |
| --- | --- | --- |
| 前端（精确判定） | **身体命中区** 158×187（`hitbox.ts::scaleHitBox`） | 命中区之外一律要求穿透 |
| 兜底通道（Rust） | **整个包围盒** 420×236（`box_rect()`） | 圈内就翻回可交互 |

包围盒里"命中区之外的那一圈"是**透明像素**（宠物周围的空白），前端判定应当穿透，
兜底却坚持翻回可交互——于是每一帧：前端翻穿透 → 兜底翻回来 → 前端再翻穿透 → …
实测表现为**那一圈时而吃点击时而不吃**：用户点了没反应、抓不住宠物
（用户两次反馈的"无法操控"都是它）。

修法：`apply_fallback_hit` 改用**与前端同一套命中几何**（`box_origin + config.hit_box`，
两边都由 `CANVAS_HIT_BOX` 等比例换算而来，Rust 与 TS 各有一份同源实现）。
两边在同一时刻必然得出同一结论，**结构上不可能再打架**。

实测（`WHALE_PET_DIAG_PRESS=drag`，一次抛掷 + 一次温柔放下）：

```text
【修复后】Rust 翻可交互=0 翻穿透=1 ；前端翻可交互=0 翻穿透=1     ← 完全一致
飞行全程没有任何翻转（光标不在身体上 → 安静地保持穿透）
```

修之前同一条路径下，每次抛掷/落地都会出现上面那种成对翻转。

## 6.7 一次真实死锁：在持锁期间跨线程改窗口样式（用户第三次反馈"现在会卡死了"）

> 这是本项目到目前为止最难定位的一个 bug。前两次（6.6 / 6.6.1）我都在**症状层**打转，
> 这次靠**进程外证据**才挖到根因。结论先写在最前面：
> **光标轮询线程持有 `state.pets` 锁去改窗口样式，而那个窗口归主线程所有。**

### 现象（用户现场日志，末尾就是断点）

```text
[pet-main-0] 松手: 甩出 速度=(-2918,-185)px/s →折扣后 (-1751,-111)px/s 位置=(1523,738)
[pet-main-0] 飞行: 开始，边界 1 块屏
[pet-main-0] 交互: 窗口切换为 点击穿透
[whale-pet] 窗口 pet-main-0：可交互=false → ex=0x80C0138 transparent=true noactivate=true layered=true
```

之后**再也不出任何一行日志**，宠物停在空中、整窗透明、点不动。第一反应容易以为是
"又有窗口在吃点击"或"渲染卡住了"，但两者都不是（视频也停在那一帧）。

### 进程外证据（四条，互相印证）

| 探针 | 结果 | 说明 |
| --- | --- | --- |
| `IsHungAppWindow` + `SendMessageTimeout(WM_NULL)` 打三个顶层窗口 | 全部 `HUNG`（2s 无响应） | 三个 Tauri 窗口都归**主线程**所有 |
| 同一探针打 WebView2 的子窗口（`Chrome_RenderWidgetHostHWND` / `Intermediate D3D Window`） | 全部 `ok`（秒回） | WebView2 侧线程**没问题** → 不是跨进程互等 |
| `Get-Process` CPU 采样 6 秒 | 应用 `+0.00s`，渲染进程 `+0.19s` | 主线程在**等**而不是死循环；页面还活着 |
| 窗口矩形截图（`CopyFromScreen`） | 只有壁纸，宠物不见 | 窗口在 (847,1033)，但内容已经不再绘制 |

### 根因：两个线程互等

```text
光标轮询线程                                  主线程（事件循环）
────────────────────────────────────────     ─────────────────────────────────
state.pets.lock()   ← 拿到锁
  runtime.apply_interactive(true)
    → window.set_ignore_cursor_events(..)
      → SetWindowLongW(hwnd, GWL_EXSTYLE)     ← 该窗口归主线程所有
         Windows 会 SendMessage(WM_STYLECHANGING)
         给主线程并**等它派发**（阻塞在这里）
                                              set_pet_bounds / pet_debug_log …
                                                state.pets.lock()  ← 等锁（被轮询线程持有）
                                                于是回不到消息循环
                                                → 上面那条消息永远派发不出去
        ××× 双方永久互等 ×××
```

- 违规点只有一处：`lib.rs::apply_fallback_hit` —— **在锁内**做了窗口操作。
  项目自己的纪律（`state.rs` 顶部）早已写着"绝不在持锁期间做 IO 或跨 webview 调用"，
  这条路径是唯一的例外，而且它跑在**非主线程**上。
- 为什么"时而卡、时而好"：死锁要求**恰好**在"轮询线程持锁做窗口调用"的那几百微秒里，
  主线程正好在等这把锁。拖拽/抛掷期间前端以 60 次/秒发命令（`set_pet_bounds` +
  每条日志一次 `pet_debug_log`），命中概率随动作剧烈程度上升——
  这与用户的观感"甩得越猛越容易卡"一致。
- 为什么上一次修复（积分窗穿透）没能解决它：那是**另一个真 bug**
  （"`show()` 之后必须补回穿透位"），与这条互等无关。用户回滚积分后仍然卡，正是这条在起作用。

### 修复（两段式 + 投递主线程）

1. `PetRuntime::plan_interactive`：**持锁期只改"意图账本"**（返回是否需要翻转），绝不动窗口；
2. `pet_window::apply_interactive_style`：只凭窗口句柄落样式，供"出锁期 / 主线程"调用；
3. `lib.rs::apply_fallback_hit` 拆成两段：① 持锁只做判定 + 记账，产出标签清单；
   ② 出锁后用 `AppHandle::run_on_main_thread` 把"落样式"**投递给主线程**（非阻塞投递）。
   于是轮询线程既不在持锁时动窗口，也不会阻塞在任何窗口调用上——**死锁环从结构上不成立**。
4. `with_pet`（前端命令那条路径）与 `broadcast_cursor` / 菜单外点关闭 / 气泡跟随取锁，
   统一改用带计时的 `watchdog::timed_lock`，让"锁被长期持有"以后一眼可见。

### 新增看门狗（`src-tauri/src/watchdog.rs`）

| 设施 | 阈值 | 作用 |
| --- | --- | --- |
| `timed_lock`（等锁计时） | 300ms 告警 / 3s 疑似死锁 | 把"锁被长期持有"变成日志里看得见的事实 |
| `timed`（窗口操作计时） | 200ms | 窗口/跨 webview 调用是唯一会"阻塞在别的线程上"的东西 |
| `MainThreadWatch`（主线程泵动） | 每秒打点，3s 无泵动告警 | **独立线程**——关键点：它不能和"嫌疑人"共用一条命 |

### 验证

**A/B 对照**：临时注入 `WHALE_PET_DIAG_LOCKSTALL=<ms>`（在 `apply_fallback_hit` 的持锁段里
人为 sleep，把竞态窗口放大到必中），用同一段真鼠标动作（光标移到宠物身上）触发：

| 组 | 代码 | 注入 | 结果 |
| --- | --- | --- | --- |
| A | 修复前（`7ee6e35`） | 250ms | **必卡死**：三个顶层窗口全部 `pump=HUNG` / `IsHungAppWindow=True`，日志停在最后一次"交互: 窗口切换为 …"翻转（与用户现场同一形态） |
| B | 修复后 | 250ms | 不卡：`pump=ok` / `IsHungAppWindow=False`，交互链路照常（穿透 → 可交互 → 点击回应） |
| B′ | 修复后 | 4000ms | 不卡，且看门狗按设计发声：`等锁 pets（前端命令）用了 ~4000ms（≥3000ms，疑似死锁…）`（连续 6 次） |

**看门狗自身的验证（进程外、零代码改动）**：用 `SuspendThread` 把主线程冻住 6 秒 →
`[whale-pet][看门] 主线程已 3015ms 没有处理任何事件（疑似死锁/长阻塞）…` ✓，恢复后应用照常。

**功能回归（真鼠标，进程外）**：悬停（就是上表的复现手法）→ 拖拽 → 松手甩出 →
**在空中再抓住** → 落地静止 → 连续 4 次真点击：`dom 按下次数 = 12`、`点击回应次数 = 4`，
全程 `pump=ok`，且**没有任何看门狗告警**（阈值不误报）。
菜单/气泡自检同样通过：`[whale-pet][自检] 气泡消失后再右键：菜单窗仍可见 ✓`。

### 教训（写给下一次）

- 症状层修三次不如一次拿**进程外证据**：`IsHungAppWindow` 一句话就把范围从
  "渲染 / 穿透 / 物理 / 窗口样式"缩小到"主线程被阻塞"。
- "谁在等谁"必须两边一起看：只看前端日志会以为"窗口卡在点击穿透"，只看 Rust 日志
  会以为"前端没发命令"。
- 看门狗必须跑在**不会被卡住的那个线程**上：第一版挂在轮询线程里，而真实死锁恰恰卡住的
  就是轮询线程——等于没有看门狗。

## 6.8 两个输入状态机的 bug：只有首次能甩出 + 穿透态按下被吞掉（用户第四次反馈）

用户反馈两句话：

1. "拖动甩出不太丝滑"；
2. "另外只有首次可以拖动甩出，后续拖动就不能甩出了"。

第 2 条是硬 bug，查下去又牵出第 1 条的一个真原因。

### 6.8.1 "只有首次能甩出"：飞行标志漏复位 + 守卫（真 bug）

- `ThrowAnimator.stop()` 按设计**不回调 `onRest`**（"被抓住"不算"落地"），
  而运行时的 `flying` 布尔量**只在 `onRest` 里复位** → 空中被抓住一次，这个标志就永远是 `true`；
- `startThrow` 开头有 `if (this.flying) return;` → 之后每一次松手都被**静默**跳过：
  日志里能看到 `松手: 甩出 速度=…`，但**没有** `飞行: 开始`。
- 复现（临时把老写法搬回来）：新增的自测 `?autotest=10` 报 **起飞 1/6**（只有第一次飞），
  与用户描述逐字一致。

**修复**：

- `flying` 改成**只读属性**，直接读 `ThrowAnimator.running`（唯一真相，结构上不可能不同步）；
- 删掉 `startThrow` 的守卫（`ThrowAnimator.start()` 内部本来就先 `stop()`，重复调用语义正确）；
- 新增 `interruptFlight()` 收口"打断飞行"（停 rAF + 取消 Q 弹），`beginPress` 与拖拽起手共用。

### 6.8.2 穿透态下"按下"被整个吞掉：兜底起手是死代码（真 bug）

`evaluateInput()` 里的原写法：

```ts
void this.setInteractive(insideBody);                          // ← 同步改写 reportedInteractive
if (primaryDown && insideBody && !this.reportedInteractive) {   // ← 于是这个条件恒为假
  this.beginPress(cursor, 'sampler');
}
```

`setInteractive()` 是同步赋值的，下一行读到的必然是自己刚设好的值——
这个分支**在任何情况下都不会命中**：窗口处于穿透态时（DOM 事件到不了页面）的按下
没有任何人处理，用户感受就是"点了没反应，得再点一次"，而 `?autotest=1/2` 这些合成自测
也因此全线失效（自测日志里全是"身体内按下未被识别"）。

**修复**：先取 `const wasInteractive = this.reportedInteractive;` 再调 `setInteractive`，
判据改成 `!wasInteractive`（"这一帧**开始时**窗口还是穿透态"才是采样兜底起手的条件）。
可交互时的按下仍走 DOM——那是零延迟、坐标最准的那条路，DOM 侧本来也有 `drag.isPressed` 去重。

### 6.8.3 新增自测钩子 `?autotest=10`（回归网）

`WHALE_PET_AUTOTEST=10` → 每轮"甩出去 → 150ms 后在空中抓住 → 再甩一次"，3 轮共 6 次起飞，
**每次都必须真的起飞**。合成输入走运行时自己的状态机（不需要真鼠标：本机上
`SetCursorPos` / `mouse_event` 会被桌面环境持续挪走，实测不可靠）。

```text
修复后：      重复甩出自测: 结果: 起飞 6/6 次 —— ✓ 每轮都成功起飞（重复甩出可用）
（临时模拟老写法）重复甩出自测: 结果: 起飞 1/6 次 —— ✗ 有甩出没有起飞（回归！）
```

顺带采到的手感数据（修复后）：

- 拖动跟随（9px/16ms ≈ 560px/s 的拖动）：弹簧滞后 **平均 41~55px、峰值 57~75px**
  —— 这是上游弹簧（K=200 / C=30）的固有滞后，不是卡顿；
- 飞行：帧步长 **平均 12~15px、峰值 46~65px**，142~234 帧**每帧都有位移**（无停顿）。

### 6.8.4 跟手手感：把随动滞后从 0.15s 压到 0.082s（用户定性反馈后定案）

用户选中了"拖动时宠物跟得太松/飘（滞后明显）"这一项。查下来的结论很干净：

- 跟手是上游的过阻尼弹簧（`SPRING_K = 200` / `SPRING_C = 30`），其**稳态滞后**为
  `v · C / K`——**与刚度无关，只由 C/K 决定**，且 `C/K = 0.15s`：
  等价于"宠物永远比光标晚 0.15 秒"，1000px/s 的拖动就落后 150px。
- 共享层的 `springStep` 带一个 `power` 参数（K/C 同乘），但它只改变**收敛速度**、
  不改变稳态滞后——所以配置里的 `throwPower` 调不出"更跟手"。

**改法（唯一一处偏离上游的物理常量，`reference/shared` 保持零改动）**：
在 `src/renderer/drag.ts` 里用同一套公式、自己的 K/C：
`K = 600`，`C = 2√K ≈ 49`（临界阻尼 ζ=1，不 overshoot）→ `C/K = 0.082s`（原 55%）。
显式欧拉的稳定步长上限 `2/√K ≈ 82ms` 仍远大于 `MAX_SPRING_DT = 50ms`（留了余量，
再往上翻倍就要提防卡顿后的抖动）。旋钮就是 `DRAG_FOLLOW_K` 这一个常量。

**验证（`?autotest=10` 的滞后采样，同一段 9px/16ms ≈ 560px/s 的合成拖动）**：

| | 平均滞后 | 峰值滞后 | 起飞 |
| --- | --- | --- | --- |
| 调之前（上游 K/C） | 41~55px | 57~75px | 6/6 |
| 调之后（K=600） | **23~29px** | **31~41px** | 6/6 |

飞行的帧步长不变（平均 13~17px、峰值 43~65px，每帧都有位移），说明只改了"跟手贴不贴"，
没有动抛掷物理。质量门同样全绿。

## 7. 纯逻辑冒烟检查

**方法**：`cargo run --bin logic-smoke`（39 项断言）。

**证据**：通过 **39 项**、失败 0 项，退出码 `0`。覆盖：

- 默认配置模板可解析并通过校验、尺寸与物理参数与上游默认值一致；
- 配置校验的四条拒绝路径（空 `pets`、非法 `id`、过小 `size`、未知 `schemaVersion`）；
- 物理参数取值范围的三条拒绝路径（恢复系数 >1、负重力、力度 0）；
- `Rect` 的右/下缘不含语义；
- `pet://` 路径防穿越（`..`、嵌套穿越、绝对路径、空路径全部拒绝）与 MIME 映射；
- 自定义协议 URL 的平台形式；
- JSONC 注释剥离（字符串里的 `//` 不被误剥、注释后的字段保留）；
- 从真实文件走完整加载路径（读文件 → 去 BOM → 剥注释 → 解析 → 校验）；
- **配置带 UTF-8 BOM 也要能读**（Windows 记事本与 `Set-Content -Encoding UTF8` 都会加 BOM；
  不加这一步就会报"第 1 行第 1 列解析失败"——实测把自己的配置文件改坏过一次）；
- **显示器几何一致性**：合法几何通过；长度不一致 / 工作区未被面板包含 / 空列表 /
  主屏零尺寸 四种坏几何全部被拒绝（与启动时的 `display::validate_geometry` 同一函数）。

**为什么不用 `cargo test`**：本机 GNU 工具链下 libtest 生成的测试可执行文件会被 Windows
加载器拒绝（`0xC0000139 STATUS_ENTRYPOINT_NOT_FOUND`）。已核对：测试程序与主程序的
**导入表逐项一致**（仅主程序多 `shlwapi.dll`），`WebView2Loader.dll` 的
`GetAvailableCoreWebView2BrowserVersionString` 导出也存在。
因此这是工具链/环境层面的问题，不是代码问题；改用独立 bin 来真正执行这些断言。

> 说明：`src-tauri/src/**` 里仍保留着 `#[cfg(test)] mod tests`（配置解析、指纹、物理校验、
> 矩形语义），它们在正常环境用 `cargo test` 就能跑；本机只是**跑不起来那个可执行文件**，
> 其断言内容已由本冒烟程序覆盖。
